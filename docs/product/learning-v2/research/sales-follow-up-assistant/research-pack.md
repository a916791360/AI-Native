- 来源登记：[`source-register.md`](./source-register.md)

## 1. 研究结论

这个案例不应被定义为「让大模型自动给客户发跟进邮件」，而应被定义为：

> 在客户信息可追溯、外发动作可授权、错误可发现并恢复的前提下，帮助销售整理上下文、形成建议草稿并记录跟进结果；首版不自动对外发送，最终发送决定始终由销售作出。

推荐方案是「信息处理 → 建议 → 决策 → 外部行动」四层分离的受限工作流：

1. 规则负责权限、客户与上下文校验、去重、版本和发送控制。
2. 模型负责汇总客户上下文、生成语气合适的跟进建议草稿，并标注依据。
3. 销售负责判断建议是否合适、修改内容、并最终决定是否发送。
4. 外部行动（发送邮件、承诺价格或条款）必须单独授权，模型不具备发送或承诺权限。
5. 首次上线只进入影子草稿，与销售当前手工流程并行验证，不替代现有流程。

## 3. 案例边界

### 3.1 教学场景

`E1 案例设定`：某 B2B 销售团队维护分散在 CRM、邮件和会议纪要中的客户信息，销售常因遗忘或信息不全而漏跟进。团队希望用 AI 帮助整理上下文并生成跟进草稿，但担心错误语气或错误承诺损害客户关系。

### 3.2 目标角色

| 角色       | 在案例中的责任                         | AI 不替代的决定              |
| ---------- | -------------------------------------- | ---------------------------- |
| 销售代表   | 维护关系、判断客户状态、编辑并发送跟进 | 是否发送、何时发送、说什么   |
| 销售主管   | 审核高风险跟进、复盘成单与流失         | 是否升级、是否批准高风险外发 |
| 销售运营   | 维护客户字段、模板与数据质量           | 字段口径与流程变更           |
| 工程或数据 | 维护接入、日志、版本与回退             | 系统异常处置与技术发布       |
| 合规或法务 | 明确可发送与不可承诺的边界             | 合规红线与授权范围           |

### 3.3 业务目标

`R 产品建议`：缩短从「识别该跟进」到「发出合适跟进」的时间，同时降低漏跟进和误发送，并保持每条建议可以回到来源。

本案例不承诺：自动成单、自动定价、自动承诺交付，或把销售经验自动转写成可执行的客户话术。

## 4. 方案取舍

| 方案                                 | 判断   | 理由                                               |
| ------------------------------------ | ------ | -------------------------------------------------- |
| 一次 Prompt 包办上下文汇总与邮件草稿 | 有条件 | 上下文与草稿步骤可生成，但需来源与版本约束         |
| 全自主 Agent 自动发送跟进            | 不推荐 | 外发动作影响真实客户关系，需逐层授权               |
| 规则 + 受限生成 + 人工发送           | 推荐   | 规则承担校验与发送控制，模型承担草稿，销售承担决定 |
| 先微调一个销售语气模型               | 暂缓   | 先建立可测基线与评测集，再判断是否需要微调         |

## 5. 责任与治理边界

- 规则承担：客户与联系人校验、权限、重复跟进、版本与发送控制。
- 模型承担：上下文汇总、建议草稿、依据标注、语气适配；不拥有发送或承诺权限。
- 销售承担：判断建议是否合适、修改内容、最终发送；高风险外发由主管复核。
- 治理范围：来源缺失、字段过期、敏感信息、重复误判、语气不当、越权承诺、超时、版本漂移与销售过载等恢复路径需逐一覆盖。

## 6. 评测、成本与上线边界

- 评测：按上下文召回、草稿相关性、语气合规、依据标注、漏跟进与误发送分别评测；不以总体准确率替代错误成本分析。
- 成本：按「成功形成一条被销售采纳的跟进」计算单位成功任务成本，含接入、模型、失败重试、运行与人工复核。
- 上线：按影子草稿、辅助草稿、受限自动草稿逐级推进；自动发送不进入首版，每级需独立通过条件与回滚路径。

## 7. 证据边界

所有业务量、采纳率、节省时长、回复率、误发率、成本与收益仍为 `E0 待验证`；外部资料只支持通用方法，不证明本案例已达标。
