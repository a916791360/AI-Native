# AI-Native 学习体系 V2 产品规格

- 状态：已批准，待实施
- 批准日期：2026-08-03
- 产品版本：Learning System V2
- 适用范围：首页、学习中心、判断题、连续案例、完整项目和知识支持层
- 视觉约束：继承已批准的「深空知识展柜」；新增页面类型必须通过 `$huashu-design` 三方向 Gate

## 1. 决策背景

AI-Native 已完成 6 阶段、24 道判断题的基础学习闭环，以及 300 个规范词条、80 个深度核验词条、4 条阅读路线和 308 条概念关系。当前产品能够帮助用户理解概念并进行单点产品判断，但还不能完整展示一个 AI 产品如何从业务问题走向方案评审、上线治理和持续迭代。

全盘结构评审形成并获用户确认的方案摘要：

> 保留现有六阶段；将 24 道题定义为基础层；增加连续案例与完整项目层；暂停部署并先完成学习体系 V2。

用户确认原话：

> 好，没问题，就这么做

外部文章中关于从业者比例和薪资的数字没有独立统计证据，不进入产品事实。文章提出的五类能力缺口——技术取舍、失败治理、业务价值、成本意识和任务拆解——作为课程覆盖检查项，并与现有内容逐项对照。

## 2. 产品定位

### 2.1 一句话定义

AI-Native 是面向中文 AI 初学者和转型产品经理的落地型 AI 产品学习系统。

### 2.2 核心承诺

用户从一个真实业务问题出发，逐步学会：

1. 判断是否需要 AI。
2. 定义业务价值与成功标准。
3. 拆解任务并选择最小可行方案。
4. 设计人机边界与失败恢复。
5. 计算质量、成本与上线约束。
6. 形成可评审、可上线、可迭代的产品方案。

### 2.3 产品不是

- 术语背诵站。
- AI 工具导航或资讯站。
- 只教用户搭建 Demo 的模板站。
- 要求用户提交长文本作业的在线课堂。
- 伪装成真实项目经验或个人学习进度的作品生成器。

## 3. 核心用户与任务

### 3.1 第一用户

希望进入 AI 产品方向的零基础或初级产品经理。他们需要建立可迁移的产品判断，而不是记忆某个供应商或工具的操作步骤。

### 3.2 第二用户

需要参与 AI 方案评审的在岗产品经理、业务负责人和非算法技术人员。他们需要快速定位一个方案在价值、能力、风险、成本和运营上的缺口。

### 3.3 核心用户任务

用户完成学习后，应能围绕一个具体业务场景回答：

- 当前问题是什么，已有流程和基线是什么？
- 为什么使用或不使用 AI？
- 规则、搜索、Prompt、RAG、工作流、Agent 或微调如何取舍？
- 任务如何拆分，工具、状态、权限和终止条件是什么？
- 哪些失败会发生，如何发现、限制影响、恢复和接管？
- 怎样定义业务指标、质量指标、单位成本和上线门槛？
- 上线后收集什么证据，如何决定继续、回滚或迭代？

## 4. 产品能力结构

```text
AI-Native
├── 唯一默认学习主线
│   ├── Level 1 单点判断：现有 24 题
│   ├── Level 2 连续案例：同一案例内连续决策
│   └── Level 3 完整项目：六个评审关卡与完整档案
├── 案例库
│   ├── 用户反馈分析
│   ├── 客服知识库
│   ├── 销售跟进助手
│   ├── 合同条款审核
│   ├── 内容生产
│   └── 内部运营自动化
├── 知识支持层
│   ├── 知识图鉴
│   ├── 搜索
│   ├── 阅读路线
│   ├── 词条详情
│   └── 概念图谱
└── 可信度层
    ├── 内容状态
    ├── 来源与日期
    ├── 方法说明

```

首页和学习中心继续只提供一条默认起点。案例库是按需浏览入口，不与主课程争夺首要行动。

## 5. 六阶段能力模型

### 阶段 01：是否使用 AI

- 核心问题：这个问题是否真的需要 AI？
- 能力：区分确定性规则、普通搜索、传统自动化与概率模型。
- 关键取舍：能用规则不使用模型；任务需要语义能力时再增加模型；模型规模按任务难度和价值选择。
- 可见产出：AI 适用性判断卡。

### 阶段 02：业务价值与数据条件

- 核心问题：这个机会值得做、能够做吗？
- 能力：描述当前流程、用户任务、业务基线、数据条件、错误成本和成功结果。
- 关键取舍：技术效果不等于业务价值；数据数量不等于数据可用；指标必须映射到真实任务。
- 可见产出：场景机会评估表。

### 阶段 03：任务拆解与方案选择

- 核心问题：怎样用最小、可靠且可验证的方案完成任务？
- 能力：拆分步骤、输入、输出、状态、工具、权限、异常与终止条件。
- 关键取舍：Prompt、RAG、工作流、Agent 和微调只解决各自范围内的问题；复杂度必须由已验证需求支撑。
- 可见产出：任务流程与方案选择表。

### 阶段 04：人机协作与失败恢复

- 核心问题：谁在什么时候做决定，失败后怎样继续？
- 能力：设计预览、确认、解释、撤销、重试、超时、人工接管和上下文传递。
- 关键取舍：动作影响越大，模型权限越小；已知失败必须提供可见的恢复路径。
- 可见产出：人机责任与失败恢复图。

### 阶段 05：评测、成本与上线治理

- 核心问题：怎样证明产品长期可用且值得运行？
- 能力：建立评测集、失败分类、线上指标、单位成功任务成本、延迟预算、监控和降级门槛。
- 关键取舍：离线分数不等于线上价值；单位调用价格不等于总成本；平均指标不能掩盖严重长尾失败。
- 可见产出：评测计划、成本表和上线护栏清单。

### 阶段 06：完整项目与持续迭代

- 核心问题：这份方案能否经得住业务、技术和运营评审？
- 能力：串联机会、方案、体验、质量、成本、发布、监控和复盘。
- 关键取舍：上线不是流程跑通，而是团队能发现失败、限制影响、承担责任并根据证据迭代。
- 可见产出：完整 AI 产品评审档案。

阶段数量和顺序保持不变；阶段标题与内容深度按本规格更新。

## 6. 三层学习方式

### Level 1：单点判断

- 保留现有 24 道题和即时反馈交互。
- 每阶段 4 题，负责建立基础判断和共同语言。
- 不再把 24 题描述为完整职业课程或完整项目。
- 题目可在后续编辑中补充关联能力、失败类型和产出片段，但不强制一次重写。

### Level 2：连续案例

- 同一业务案例由多个连续决策节点组成。
- 前一节点的选择会改变当前页面展示的后果、约束或方案片段，但不保存为个人进度。
- 用户通过选择、展开、对比和查看批注学习，不填写长文本。
- 每个案例至少覆盖现状、价值、方案、异常、指标和复盘中的三个部分。

### Level 3：完整项目

- 使用同一个业务对象连续通过六个阶段，不把四个无关场景包装成一个项目。
- 每个阶段展示一份逐步形成的标准产品材料。
- 项目结束时呈现完整档案，并标明哪些判断来自事实、哪些是方案选择、哪些仍需验证。
- 首个完整项目固定为“每日用户反馈分析与产品改进”。

## 7. 连续案例内容契约

### 7.1 Case

每个案例至少包含：

| 字段              | 说明                                           |
| ----------------- | ---------------------------------------------- |
| `id`              | 英文 ASCII 稳定 ID                             |
| `title`           | 中文案例标题                                   |
| `level`           | `focus` 或 `capstone`                          |
| `domain`          | 业务领域                                       |
| `audience`        | 适用学习者                                     |
| `businessContext` | 业务背景与触发事件                             |
| `currentProcess`  | 当前流程与责任角色                             |
| `objective`       | 可观察业务目标                                 |
| `baseline`        | 已知基线；未知时明确标记待验证                 |
| `constraints`     | 数据、风险、成本、权限或时间约束               |
| `gates`           | 有顺序的决策关卡                               |
| `artifacts`       | 学习过程中形成的标准材料                       |
| `references`      | 关联词条、路线和来源                           |
| `status`          | `planned`、`draft`、`verified`、`needs-review` |

### 7.2 Gate

每个关卡至少包含：

| 字段            | 说明                             |
| --------------- | -------------------------------- |
| `id`            | 案例内稳定 ID                    |
| `stageId`       | 对应六阶段之一                   |
| `question`      | 当前必须作出的产品决定           |
| `facts`         | 作出判断时已经知道的事实         |
| `unknowns`      | 当前不能假装已知的事项           |
| `options`       | 至少两条具有真实取舍的路径       |
| `feedback`      | 每条路径的价值、条件、风险和后果 |
| `artifactDelta` | 本关卡为标准材料新增的内容       |
| `failureModes`  | 已识别失败及影响                 |
| `metrics`       | 本关卡需要观察的业务或技术结果   |
| `references`    | 相关词条和来源                   |

### 7.3 标准材料类型

V2 使用六种可见材料，不要求用户填写：

1. AI 适用性判断卡。
2. 场景机会评估表。
3. 任务流程与方案选择表。
4. 人机责任与失败恢复图。
5. 评测、成本与上线护栏表。
6. 完整 AI 产品评审档案。

## 8. 首个黄金项目

### 8.1 项目名称

每日用户反馈分析与产品改进。

### 8.2 业务链路

```text
收集反馈
  → 清洗与去重
  → 分类问题
  → 聚类高频主题
  → 统计 Bug 与影响
  → 生成证据化建议
  → 人工确认
  → 发布日报
  → 记录修正与结果
```

### 8.3 六个评审关卡

1. 定义业务问题、当前人工流程和成功结果。
2. 判断每一步使用规则、模型或人工的边界。
3. 拆解工作流、工具、状态、优先级和终止条件。
4. 处理接口失败、重复数据、标签漂移、幻觉建议和人工接管。
5. 定义分类质量、主题覆盖、人工节省、单位处理成本和延迟预算。
6. 设计影子运行、抽样复核、告警、回滚和迭代记录。

具体阈值、数据量和业务收益在案例研究完成前保持待验证，不使用虚构数字。

## 9. 页面与信息架构职责

### 首页

- 解释“落地型 AI 产品经理学习系统”的定位。
- 展示唯一默认起点和三层学习结构。
- 不把案例库、词库或某一道题提升为同权主入口。

### 学习中心

- 展示六阶段能力模型和 Level 1–3 的关系。
- 默认引导新用户从 Level 1 第 01 题开始。
- 已有基础的用户可以按需进入连续案例，但入口保持次要层级。

### 单点判断页

- 保留情境、事实、选择、即时反馈、原则、检查项和下一题。
- 明确标注这是基础训练，不暗示已经完成项目交付。

### 连续案例页

- 显示案例上下文、当前关卡、已形成材料和后续影响。
- 允许选择、展开、比较、切换材料视图；不提供长文本输入。
- 只在当前浏览会话展示选择效果，不写入账号、本地进度或远端数据。

### 完整项目页

- 使用六个评审关卡展示同一个项目的完整演进。
- 项目结束后提供可阅读的标准评审档案和来源。
- 不把标准答案描述为唯一行业做法；说明适用条件和待验证项。

### 知识支持页

- 图鉴、搜索、路线、词条和图谱继续按需提供解释和证据。
- 首页数字使用“深度词条”等用户可理解名称；`verified` 作为内容方法状态保留在详情和方法说明中。

## 10. 交互与视觉原则

- 不要求用户输入文字、上传资料或提交作业。
- 不登录、不保存个人选择、不制造完成百分比。
- 点击选择必须立即展示取舍依据，不只显示“正确/错误”。
- 同一页面只保留一个明确的继续动作。
- 不通过多个同权入口重复包装同一内容集合。
- 新增案例页和项目页在生产开发前必须使用 `$huashu-design` 输出三套真实 HTML 方向稿与双端截图；用户选择后再转译为 Astro 生产组件。
- 三套方向必须继承现有品牌 Token，不重新选择品牌风格。

## 11. 内容资产的保留与扩展

### 保留

- 现有 24 道判断题。
- 300 个规范词条和 80 个深度核验词条。
- 4 条已发布阅读路线。
- 308 条概念关系。
- 搜索、图谱、来源、状态和修订机制。

### 新增

- 连续案例和关卡内容模型。
- 完整项目档案模型。
- Agent 任务拆解、评测治理、成本治理和上线运营的路线覆盖。
- 案例与词条、路线、关系之间的结构化引用。

### 不进入 V2 首批

- 账号和云端进度。
- 文本作业和自动评分。
- AI 聊天老师。
- 证书、社区、付费和求职承诺。
- 自动生成或伪装个人作品集。

## 12. V2 首批范围

V2 首批包括：

1. 保留并重新定位 24 道基础判断题。
2. 完成一个“每日用户反馈分析”黄金完整项目。
3. 完成客服知识库、销售助手、合同审核、内容生产和内部运营自动化五个重点案例。
4. 补齐与六阶段对应的阅读支持，优先覆盖任务拆解、评测、成本和上线治理。
5. 完成首页、学习中心、案例页和项目页的信息架构升级。
6. 完成目标用户任务型验收后，才恢复部署决策。

## 13. 可观察验收标准

### 产品理解

- 首次进入的用户能指出唯一默认起点。
- 用户能区分 24 题基础训练、连续案例和完整项目的作用。
- 用户不会把四个无关案例误解为同一个综合项目。

### 能力迁移

- 用户能在新场景中说明为什么使用或不使用 AI。
- 用户能把一个 Agent 场景拆成步骤、工具、状态、异常和终止条件。
- 用户能指出至少一个业务指标、质量指标、成本口径和失败恢复路径。
- 用户能根据完整档案复述方案的价值、限制、上线门槛和下一轮验证。

### 体验

- 用户无需填写文字即可完成全部学习路径。
- 选择后的反馈、材料变化和下一步均可被键盘与屏幕阅读器访问。
- 禁用 JavaScript 时仍能阅读默认案例路径、标准材料和知识引用。

### 内容可信度

- 案例事实、假设、建议和待验证项明确区分。
- 每个关键判断关联至少一个可复核词条或来源。
- 案例状态与实际完成度一致，草稿不冒充已核验项目。

## 14. 风险与依赖

| 风险或依赖               | 影响                   | 处理原则                                  |
| ------------------------ | ---------------------- | ----------------------------------------- |
| 只增加题量               | 用户仍只会选答案       | 以连续案例和可见材料作为扩展单位          |
| 案例数字虚构             | 破坏内容可信度         | 未研究数据明确标记待验证，不伪造收益      |
| 页面入口再次膨胀         | 用户不知道从哪里开始   | 保持唯一默认主线，案例库为次要入口        |
| 视觉先于内容             | 原型好看但无法训练能力 | 先批准内容契约，再进入 Huashu Design Gate |
| 静态交互被误解为进度     | 形成虚假学习记录       | 明确只在当前页面反馈，不保存完成状态      |
| 原技术发布候选被直接部署 | 上线过时的产品定义     | 部署顺延到 V2 用户验收之后                |

## 15. 决策与待验证边界

### 已确认

- 产品升级为落地型 AI 产品学习系统。
- 保留六阶段、24 题和现有知识资产。
- 增加连续案例与完整项目层。
- 用户通过查看、选择和比较学习，不填写长文本。
- 首个黄金项目为每日用户反馈分析。
- V2 验收前暂停部署。

### 待通过研究或测试确定

- 每个重点案例的具体业务数据、阈值和来源。
- 连续案例最适合的关卡数量和页面长度。
- 用户是否能在不记录进度的情况下理解跨案例位置。
- 新增案例页的最终视觉结构。
- 目标用户完成任务所需时间和可接受卡点范围。
