一、结论摘要

这个站的瓶颈不是内容太少，而是内容太多、且没有组织逻辑。 325 个词条的产量已经明显超过维护能力，但用户拿到的不是一个「能走通的理解路径」， 而是一个按 13 个学科领域归档的档案柜。

三个数字可以概括全部问题。它们不是抽样印象，是对全部 325 个词条逐字符扫描的结果：

8 / 325八个二级标题
覆盖全部 325 个词条
一致性 100%
220 / 325词条正文逐字复用
同一批模板句
占比 67.7%
34 / 325词条被纳入阅读路线
其余 89.5%
没有任何顺序引导

第一个数字说明没有一条词条拥有属于自己的结构；第二个说明三分之二的词条正文是填空产物； 第三个说明近九成词条孤立在路径之外。三者叠加，得到用户的实际感受： 三百多条目，点进去每条都长得一样，读完记不住区别，也不知道下一条该看什么。

核心判断

站点已经把「结构治理」做过一轮——顶栏从两套名词收敛到三项、板块命名收敛到唯一事实源 （src/config/sections.ts），这说明信息架构的混乱曾经被识别并修复过。 但同样的治理从未施加在内容上：13 个学科领域是照搬教科书分类， 它回答「这个名词属于哪个学科」，不回答学习者真正的问题——「这些东西之间是什么关系、我该按什么顺序理解」。

因此本报告的重心不是「再写一批词条」，而是三件事： 给词库加上第二条坐标轴（认知链路）、 把词条从「名词解释」改成「决策页」、 把内容质量也纳入已有的工程门禁。

三、用户体验：导航与路径

四个问题，按严重度排列。

UX-01 P1

学习页侧栏是「3 层 × 6 模块」，产生 18 个同名条目

这正是你提到的「同层级菜单命名重复且无实际意义」的最准确落点。 学习页左栏的结构是：三个层（T1 概念识别 / T2 场景判断 / T3 权衡取舍）， 每一层下面列出同样那六个阶段。

于是侧栏渲染出 18 个链接，而显示文字里： 「AI 基础与模型边界」出现 3 次、 「场景与机会判断」出现 3 次、 「方案选择」出现 3 次……六个名字各重复三遍。

它们的锚点其实不同（#module-T1-01 / #module-T2-01 / #module-T3-01）， 但用户看不到锚点，只看到文字。面对 18 行里 6 个名字各出现三遍的菜单， 人无法判断该点哪一个——这不是「难用」，是菜单失去了指示能力。

代码位置：src/components/learning/LearningCatalog.astro L26–30 — 三层各自的 <ul> 遍历的是同一个 LEARNING_MODULES 数组。
UX-02 P1

同一个内容池有四套入口，且四套的分类法互不映射

现在同时存在四层入口体系：

  • 顶栏 3 项：开始学习 / 案例库 / 知识库
  • 页脚 6 项：以上 3 项 + 阅读路线 / 概念图谱 / 搜索，另加「内容方法」与 GitHub
  • 页内左栏：知识库是 13 个学科领域；学习页是 3 层 × 6 阶段
  • 页内锚点：词条页是「内容概览 / 概念关系」

问题不在「入口多」，而在四套入口用的是四套不同的分类法， 彼此无法翻译。用户从顶栏「知识库」进入，看到的是 13 个学科领域； 点开一个词条，右栏叫「概念关系」；想按顺序读，得退回页脚找「阅读路线」。 每下一层，都要重建一次心理模型。

代码位置：src/config/sections.ts（顶栏 / 页脚） · src/pages/atlas/index.astro（13 领域左栏） · src/pages/terms/[id].astro（页内锚点）。
UX-03 P2

全站没有面包屑，深层页面只能「回列表」

src/components/layout/ 下只有三个组件：SiteHeader、SiteFooter、PageIntro， 没有面包屑组件。而这个站的页面深度并不浅：

  • 词条页：知识库 → 13 个领域之一 → 词条，两层
  • 答题页：学习库 → 某层 → 某阶段 → 某题，三层
  • 案例关卡页：案例库 → 案例 → 关卡，两层

325 个词条页 + 90 个答题页 + 6 个案例的多级关卡页，进入之后都没有一条 「我在哪里、怎么回去上一层」的常驻指示。用户靠浏览器的后退键导航， 这意味着站内的层级结构在体验上是不存在的。

UX-04 P1

首页第一屏就把零基础用户推进第 01 题

首页 hero 的主按钮直接是「从第 01 题开始 →」，跳转到 /learn/questions/q01-rules-or-ai/。

对一个「AI 零基础用户」来说，第一屏的唯一主动作是立刻做一道判断题， 而此刻他连题目里可能出现的基本词汇都还没有。 更矛盾的是，同一屏的副标题写着「不是背名词，而是学会判断」—— 可判断的前提恰恰是先有名词。这个站有完整的词库和五条路线， 却在入口处把它们全部跳过了。

首页往下第三屏才是「知识库」的介绍，但那时用户已经被引导走了。 引导的次序反了：应该是「先建立共同语言 → 再做判断 → 再看完整案例」。

代码位置：src/components/home/HomeLanding.astro L33 — href="/learn/questions/q01-rules-or-ai/"。

四、学习成效：内容组织

这是最根本的一组问题，也是「词库读不懂」的真正成因。

LN-01 P0 · 根本

用「学科分类法」承载「学习路径」——两件事被混为一谈

知识库用 13 个学科领域组织全部词条：AI 基础与发展史、机器学习与深度学习、 大语言模型与生成式 AI、提示词与上下文工程、多模态、数据检索与 RAG、 Agent 与工具调用、AI 产品与用户体验、评估与可观测性、AI 工程运维、 安全伦理与治理、算力芯片与产业、AI 产品经理基本功。

这是一份教科书目录。它天然适合「查阅」——当我明确知道要找什么时， 我知道该翻到哪一章。但它不表达任何依赖关系： embedding 和 agent-memory 被平等地放进两个领域， 读者无法从中得知「先有 Token，才谈得上上下文窗口；先懂检索，RAG 才有意义」。

关键区分

分类法回答「它属于哪个学科」；学习路径回答「我该先理解什么」。 这两件事需要两套坐标，而站点目前只有一套。 这就是为什么 325 个入口在体验上等于零个入口—— 每个入口看起来同等重要，用户无法做任何决策。

站点在「结构」层面其实已经理解了这个问题的一部分：阅读路线就是按目标场景而非学科来串词条的。 但它只覆盖 34 条，且被放在页脚，正确的机制被用在了最小的规模上。

LN-02 P0

三个内容库互不连通，学习闭环只通一半

对全部 325 个词条做外链方向的统计，结果是：

链接方向覆盖数含义
词条 → 判断题 0 / 325 读完一个概念，无法立刻做题验证
词条 → 案例 0 / 325 读完一个概念，看不到它在真实业务里的样子
词条 → 阅读路线 1 / 325 只有一条词条知道自己归属哪条路线
判断题 → 词条 有（references 字段） 答题页有「按需深挖」区，能跳进词条

引用是单向的：从「做题」可以回到「看概念」， 但从「看概念」到不了「做题」。而学习闭环需要的恰恰是双向循环—— 概念建立预期，题目检验预期，案例提供真实语境。

实际后果：一个用户在知识库读了 20 个词条，他没有任何机会知道 「这个概念对应哪道题、哪个案例」。他读完就离开了， 90 道精心校验过的题和 6 个写得不错的案例，与 325 个词条之间没有通路。

LN-03 P1

89.5% 的词条没有顺序引导，且「相关推荐」是模板分配的

五条阅读路线声明覆盖 55 个词条，实际覆盖 34 个。 剩下的 291 个词条（89.5%）不属于任何路线， 因此词条页底部的「上一个 / 下一个」不渲染。

这些词条唯一的引导，是正文末尾那句「接下来学什么」。它的形态是：

接着阅读 [X] 与 [Y]，把这个概念放回更大的关系网里。

全量统计后：这 325 段推荐只产生了 48 种不同的链接组合—— 同一个组合最多被 24 个词条共用。 也就是说，从十几个不同概念出发，用户会被引导到完全相同的两个地方。 推荐不是基于语义邻接计算的，而是按领域和优先级批量分配的。

最典型的组合：24 个词条的「接下来学什么」都是 算力 → 人工智能；另有 23 个都是 人工智能 → 生成式 AI； 20 个都是 AI 应用 → 人工智能。
LN-04 P2

「概念图谱」画得出网，但网里没有语义

图谱数据 graph.json：325 个节点、333 条边，0 个孤立节点。 单看这组数字，图谱是完整的。但边类型分布是：

边类型数量占比来源

prerequisite（前置）82.4%人工撰写
component（组成）72.1%人工撰写

人工撰写的语义关系在 src/data/relations.yml 里只有 20 条， 而词条有 325 个。其余 315 条边是为了让图谱看起来连通而补上的同一类型边。

这产生了一个比空白更糟的结果：用户看到一张密集的网， 会以为里面编码了知识结构，于是花时间去看。 但一张 94.6% 的边都是同一种类型、且不区分方向的网， 传达不了任何结构信息。 初学者最需要的那类关系——「A 是理解 B 的前提」——恰恰只有 8 条。

五、实际可用性：词库质量

这一节是全报告最严重的部分。「300 多个条目结构庞杂、难以理解、实际使用价值低」 是一个准确的感受，下面说明它为什么会这样，以及严重到什么程度。

KB-01 P0 · 最严重

325 个词条 100% 共用同一套八段模板

对全部 325 个词条做标题结构扫描，结果没有任何例外：

二级标题出现次数
它是什么325 / 325
为什么需要它325 / 325
它如何工作325 / 325
真实例子325 / 325
什么时候适合与不适合325 / 325
亲自试一下325 / 325
接下来学什么325 / 325
来源与修订325 / 325

八个标题本身是好的设计——它们覆盖了理解一个概念所需的完整面向。 问题在于每条都一模一样：正文长度集中在 791–1576 字符， 均值 1113，分布异常收紧。 「向量数据库」和「AI 产品经理胜任力」这两个概念，需要的篇幅和结构不可能相同。 如此均匀的长度只说明一件事：内容是被插进模板的，不是被写出来的。

KB-02 P0 · 最严重

220 个词条（67.7%）的正文逐字复用了同一批句子

这是「读了等于没读」的直接原因。以下几句话， 在 220 个不同的词条里一字不差地出现： 

「它通常先确认输入、约束、流程和输出，再检查这些部分能否被复核。
 这样做可以把抽象名词落到具体判断上」

「它适合被用来统一语言、减少歧义和梳理边界，但不适合被当成万能解释。
 若定义太粗，容易掩盖条件差异；若过早套用，也会把本来简单的问题说复杂」

「把【概念名】放进你正在看的一个真实项目里，写下三件事：
 它是什么、它不是什么、什么时候不该用它」

「【来源 A】和【来源 B】会是很好的核验起点」

关键在于：这些句子对任何概念都成立，因此对任何概念都不提供信息。 「先确认输入、约束、流程和输出」既适用于向量数据库，也适用于绩效考核。 把这样的句子放进 220 个词条的「它如何工作」下面， 读者每一篇都花了时间，却每次都没有获得该概念的任何具体知识。

实例解剖 · MCP 词条

MCP 是受众最关心、也最容易搞混的概念之一，正好可以看看模板产出了什么。 文件：src/content/terms/agents-tool-use-automation/model-context-protocol.mdx

  • 「它如何工作」写的是： 「它通常先确认输入、约束、流程和输出，再检查这些部分能否被复核」—— Host / Client / Server 三个角色、JSON-RPC、Resources / Prompts / Tools 三类能力，一个都没出现。而这恰恰是 MCP 的全部机制。
  • 「真实例子」没有例子，只有一句 「在一个真实的 Agent 与自动化场景中，团队会先把模型上下文协议放进当前问题里」。
  • 引用来源与内容不匹配：词条引用的两篇是 Anthropic 的 《Building Effective Agents》与《Trustworthy Agents in Practice》—— 这两篇都不是讲 MCP 的，前者讲 Agent 的设计模式。 MCP 的权威来源是协议规范本身（modelcontextprotocol.io）。
  • 最危险的后果：读者读完会形成「MCP 是一种梳理边界、统一语言的方法」 这种印象，而它实际是一个标准化的接口协议。 这不是内容为空，是内容给出了错误的认知框架。
KB-03 P0

词条数量由配额决定，不由知识需求决定

两个数字碰在一起，暴露了生产方式：

  • src/lib/content/schema.ts L37：z.array(domainSchema).length(13) —— 领域数硬编码为 13
  • 每个领域目录下的词条数：全部恰好 25 个（13 × 25 = 325）

「AI 基础与发展史」「机器学习」「算力芯片与产业」「AI 产品经理基本功」—— 这四个领域的知识边界和体量差异极大，不可能真的都恰好需要 25 条。

配额制的后果是结构性的： 当「凑够 25 条」成为约束，就必须拆分本不该拆的概念（见下一个问题）， 或者为凑数引入次要条目。内容的粒度被配额绑架了，而不是被读者的理解需要决定。

一个初学者看到「检索」「上下文检索」「检索查询」三个平级条目， 没有任何线索判断它们的差别、更不知道该先点哪个。 而按配额逻辑，这个领域必须凑满 25 条，于是同一件事的各个侧面被拆成了独立页面。

RAG 有词条，且路线「RAG 从零到理解与应用」覆盖它 相对最好，但被埋在
25 条检索碎片里，入口不显眼

这个缺口的性质值得单独说：缺的不是词条数量，是「概念之间的边界说明」。 MCP 与 Skill、MCP 与 LangChain、Agent 与 Workflow、 RAG 与微调——这四组边界，是用户真正卡住的地方。 而模板化的词条结构里，没有任何一处是为「和邻居的差别」预留的。

KB-06 P1

「亲自试一下」这个标题下面是零上手

325 个词条里，220 个的「亲自试一下」写的是同一句话： 把概念放进你的项目里，写下三件事——它是什么、它不是什么、什么时候不该用它。

这个动作对「梳理思路」有点用，但它不解决「上手」，而且被放在了 一个承诺「试一下」的标题下面。真实的差别是：

概念模板给的动作真正的「上手」是什么
MCP 写下三件事 装一个官方 MCP Server，在客户端里连上，
看到工具出现在工具列表并能读一个本地文件
Skill （词条不存在） 写一个 20 行的 SKILL.md，
观察它何时被加载、何时不被加载
RAG 写下三件事 拿 5 份真实文档跑一次检索，
故意问一个「资料里没有」的问题，看系统如何处理
Agent 写下三件事 给模型两个工具（读文件 + 写文件），
让它完成一次多步任务，观察你在哪一步必须介入

「上手」的定义是可观察的行为变化：你做完之后， 你的环境里多了一个东西、或者你亲眼看到了一个现象。 「写下三件事」不产生这两种结果。

六、成因分析

上面 14 个问题不是 14 个独立的疏忽，它们由四个根因产生。 找到根因的价值在于：修问题只能修 14 次，修根因可以防止它们再长出来。

根因一：产量驱动，而非需求驱动

先定下「13 个领域 × 25 条 = 325 条」这个数字，再用模板把数字填满。 证据链完整闭合：schema.ts 硬编码领域数 13 → 每个领域恰好 25 条 → 八个标题在 325 条里 100% 一致 → 220 条正文逐字同句。

当「产出量」是目标时，「这一条该不该存在」「这一条对读者有没有增量」 就不再是决策点，而变成了阻碍交付的麻烦。 配额制度把内容决策降级成了填充作业。

根因二：把「分类法」当成了「学习路径」

站点做过一轮信息架构治理——顶栏从两套名词收敛到三项、 板块命名收敛到 sections.ts 这一个事实源， 文件头注释里甚至记录了一次「典型的信息架构事故」。 这说明结构的混乱已经被识别、被修复过。

但那一轮治理解决的是命名问题，没有触及顺序问题。 13 个学科领域是照搬教科书分类，它对「这个名词属于哪个学科」回答得很好， 对「我该先理解什么」完全没有回答。 命名收敛了，认知路径仍然是 325 个平级入口。

根因三：三个内容库由三条独立流水线生产，缺少共同的用户旅程锚点

三个模块的质量控制水平差异极大：

  • 90 道判断题：有契约校验， scripts/check-learning-bank.ts 会逐题检查形态， 任何一层出现不达标的题都会让构建失败——质量受控。
  • 6 个案例：手工撰写，有真实业务背景、当前流程、风险条件——质量受控。
  • 325 个词条：模板批量生成，没有任何内容质量门禁—— 而这恰好是体量最大、用户接触最多的模块。

更关键的是三者之间只有「题目 → 词条」这一个单向引用。 没有任何一个环节在负责「用户从进入网站到能上手一个概念」这条完整路径。 每个模块都在自己的职责范围内做得不错，但它们没有被同一条用户旅程串起来。

根因四：选错了可验证的指标

这个项目在工程侧做得相当好，已经建立了： 性能预算（src/data/performance-baseline.json）、 设计守卫（pnpm check:design 禁止中间字重、要求字重落差 ≥ 300）、 内容契约校验（学习题库）。这些都是把「隐性标准」变成「可自动检查的红线」。

但内容侧没有对应的守卫。没有脚本检查 「这条词条是不是只是模板」、「这个领域是不是装了不该拆的概念」、 「同一领域内是否出现了近义碎片」。

一句话总结根因

能被测量的东西被持续优化了，不能被测量的东西——内容与读者理解需求的匹配度——被忽略了。 这不是团队能力问题，是「可验证性」决定了注意力的分配。 解法就是把内容质量也变成可验证的。

七、改进建议

四个方向，按依赖关系排列。方向一是地基，其余三个都建立在它上面。

方向一｜给词库加上第二条坐标轴：从「学科分类法」到「认知链路」

核心动作：在 13 个学科领域之上，增加一层「认知链路」， 用 8 站把用户从「不知道从哪开始」带到「能自己走了」。

这 8 站不是凭感觉排的，它对应的是业界当前对这套技术栈的共识理解—— 整条链路在回答同一类问题：语言模型缺什么，每一层补什么。

  1. 01地基 · 模型是什么LLM 的概率本质、Token、上下文窗口、能力边界。回答「它为什么不是检索、也为什么必然会编」。
  2. 02沟通 · 怎么把需求说清楚Prompt 与上下文工程。回答「为什么同样的模型，别人用得比你好」。
  3. 03给知识 · 怎么让它知道你家的资料RAG：切片、向量化、检索、重排。回答「怎么让它答我司的内部问题」。
  4. 04给手脚 · 怎么让它做事Agent：工具调用、规划、记忆、人机介入点。回答「怎么从给答案变成把事办完」。
  5. 05给接口 · 怎么标准化地接系统MCP：Host / Client / Server，一次对接处处可用。回答「为什么每个工具不再各接一遍」。
  6. 06给流程 · 怎么把做法沉淀下来Skill / SOP：把「这件事该怎么做」写成可复用模块。回答「怎么不每次都从头教一遍」。
  7. 07给判断 · 怎么知道它行不行评估、观测、成本与延迟。回答「上线之后，你凭什么说它变好了」。
  8. 08给安全 · 什么时候必须有人管护栏、权限、最小授权、human-in-the-loop。回答「哪些动作永远不能让模型自己决定」。

关键设计约束：这 8 站不是第 14 个领域，而是词条的第二套坐标。 每个词条同时拥有两个位置—— 学科归属（它在档案柜的哪一格，用于查阅）和 链路位置（它在理解路径的第几站，用于学习）。 前者服务「我知道要找什么」，后者服务「我不知道要找什么」。两套坐标必须同时存在， 不能用一套替换另一套。

方向二｜把词条从「名词解释」改成「决策页」

现在的词条在回答「X 是什么」。读者读完之后，仍然无法回答三个真正的问题。 建议把词条的目标重写为读完能回答这三问：

  1. 它解决什么、不解决什么？（边界，而不是定义）
  2. 它和最容易混淆的邻居差在哪？（这个站现在完全没有为这个预留位置）
  3. 我今天能拿它做什么？（一个可完成的最小动作）

相应地，八段模板的「来源与修订」可以保留（这个设计是好的）， 但「它如何工作」必须填入真实的组件名与流程， 「真实例子」必须是真的例子，「亲自试一下」必须换成可执行动作。 模板结构可以留，模板句子必须清空。

八、五个概念的示范性组织

MCP、Skill、Agent、LangChain、RAG——这五个是你点名的概念， 也是当前受众「听说过、说不清」的典型。它们值得单独设计，原因有两个：

  1. 它们不是五个并列的名词，而是一条链上五个不同层次——这正是最难传达的部分；
  2. 用户对它们的困惑有高度重复的模式：能说出名字，说不出边界，因此容易糊成一团。

先建立总图：五个概念各在哪一层

概念它所在的层一句话定位用户最常见的困惑
MCP 接口层 怎么标准化地把模型接到外部工具和数据 「它和 Function Calling 是什么关系？」
Skill 流程层 怎么把「这件事该怎么做」沉淀成可复用的 SOP 「它和 Prompt、和 MCP 又是什么关系？」
Agent 控制层 模型自己规划、行动、观察、再规划的循环 「它和 Workflow 到底差在哪？」
LangChain 实现层 用代码把上面这些编排起来的框架 「它和 MCP 是不是竞品？」
RAG 知识层 回答之前先查你自己的资料 「它和微调该选哪个？」
这张表本身就是缺失的内容

站点目前没有任何一个页面在回答「这五个词之间是什么关系」。 它们分散在 13 个领域中的两个里，彼此之间没有链接。 对受众而言，这张表的价值大于其中任意五篇词条。 建议把它做成链路第 4–6 站的引导页。

每个概念该怎么写：五个具体示范

下面给出每个概念的必备要素——不是完整稿， 而是「这一条必须出现什么、必须澄清什么误会、上手动作是什么」。 判定标准很简单：一个读者读完，能不能向同事复述出它的边界。

MCP（模型上下文协议）

  • 定位必须写清：它是一个接口标准， 不是工具本身、不是框架、不是模型能力。 类比可用「AI 世界的 USB-C」——一次对接，处处可用。
  • 机制必须出现：三个角色 Host / Client / Server； 通信基于 JSON-RPC 2.0； Server 能向客户端提供三类能力——Resources（数据）/ Prompts（模板）/ Tools（可执行动作）； 传输方式分本地 stdio 与远程 HTTP。
  • 必须澄清的误会： MCP ≠ Function Calling——后者是各模型厂商自家的调用格式， 前者是把「工具接入」这件事标准化的协议； MCP ≠ LangChain——两者在不同层，可以叠加使用。
  • 必须提到的局限：MCP 是连接标准，不是安全保险柜。 规范本身就建议保留 human-in-the-loop、向用户明确展示工具调用并允许否决。 第三方 Server 应视为不可信来源。
  • 上手动作（约 15 分钟）：装一个官方 filesystem MCP Server， 在支持 MCP 的客户端里连上，看到工具出现在工具列表，并成功读到一个本地文件。 观察点：这一步不需要改任何代码。
  • 权威来源：协议规范（modelcontextprotocol.io）， 而不是一篇讲 Agent 设计模式的博客——这正是现在词条引用的东西， 也是它给出错误框架的原因。

Skill（Agent Skills）— 当前完全缺失

  • 定位：程序性知识的封装—— 回答「这件事该怎么做」，而不是「能访问什么」。 一个 Skill 就是一个目录 + 一个 SKILL.md （带 YAML frontmatter 的 name 与 description），可以附脚本与参考文件。
  • 机制核心是「渐进式披露」：未被激活时， 模型只看到每个 Skill 的名字和描述；只有相关时才读全文。 这一点必须讲透——它是「为什么可以装几十个 Skill 而不撑爆上下文」的答案， 也是最容易被误解为「就是个长 Prompt」的地方。
  • 必须澄清的误会（最重要的一条）： Skill 与 MCP 是互补而非竞争。 业界官方表述可以直接引用： 「MCP 给模型工具访问权限，Skill 教它如何有效地使用这些工具。」 Skill 也不等于 Prompt：前者按需动态加载、跨会话存在、可携带代码资产； 后者是单次对话内的一次性指令。
  • 必须提到的现状：Agent Skills 规范已作为开放标准发布， 同一份 Skill 格式可在采纳该标准的多个平台上使用——这解释了它为什么重要。
  • 安全提醒（不能省）：第三方 Skill 应视为不可信代码。 一个恶意 Skill 可以指示模型执行命令或调用工具，且行为可能与其声称的用途不符。 装之前通读，必要时在沙箱里跑。
  • 上手动作（约 20 分钟）：写一个 20 行的 SKILL.md （例如「本团队周报的固定格式」）， 然后观察它何时被加载、何时不被加载。 观察点是「触发条件」，不是「输出质量」——这是理解 Skill 的关键。

Agent（智能体）

  • 定位必须打掉一个直觉：Agent 不是「更聪明的聊天机器人」， 而是一个循环——规划 → 行动 → 观察结果 → 再规划，直到任务完成。 聊天机器人负责「说」，Agent 负责「做」。
  • 必须给出与 Workflow 的分界线：这是用户最常问的。 一句话——路径由人预先定死的是 Workflow；路径由模型在运行时决定的是 Agent。 两者不是先进与落后，是适用场景不同：流程稳定就该用 Workflow，因为它可预测、可审计。
  • 机制必须出现：工具调用是「能动手」的开关（模型输出结构化指令 → 外部程序执行 → 结果回喂 → 模型基于结果继续）； 记忆分短期（当前上下文窗口内）与长期（写入外部存储）； 自主度是一个可调的旋钮，不是有/无的开关——从「模型只填空」到「完全自主」之间有很多档， 生产环境通常落在偏保守的一端。
  • 必须写清的风险：一旦允许写文件、跑命令、发消息， 错误的性质就从「说错话」升级为「做错事」。 所以护栏、权限控制、人类可否决，不是附加项而是必需品。
  • 上手动作（约 30 分钟）：给模型两个工具（读文件 + 写文件）， 交给它一个多步任务（例如「把 A 文件里的清单整理成表格写进 B 文件」）， 观察它在哪一步需要你介入。 观察点是「介入点出现在哪里」——这直接对应生产环境的审批设计。

LangChain — 当前完全缺失

  • 定位：应用层的编排框架—— 一个跑在你自己的进程里的代码库，不是一个协议，也不是一个服务。 它帮你把「调模型、接工具、管记忆、组链条」这些重复劳动封装起来。
  • 必须出现的对比维度：工具定义方式（代码装饰器 vs 独立服务进程）、 发现方式（写死在应用里 vs 连接时动态发现）、 复用范围（跨项目复制代码 vs 装一次任何兼容客户端都能用）、 运行位置（你的进程内 vs 独立进程）。
  • 必须澄清的误会：LangChain 和 MCP 不是竞品，它们在不同层。 可以给一句可操作的决策规则： 缺工作流控制，用 LangChain；缺标准化接入，用 MCP；两者都需要时叠加使用。 同时应提到它在生态中的演进（图式、状态化编排的路线在生产环境中更常被选中）。
  • 上手动作（约 30 分钟）：用约 30 行代码跑通一条最小链 （检索 → 拼提示 → 生成）， 然后把同一个检索换成由 MCP Server 提供的工具，体会分层的差别。 这个对比动作是本条词条存在的全部理由。

RAG（检索增强生成）

  • 定位：知识层——回答之前先去你的资料里查一次， 让模型「开卷答题」，而不是把知识塞进模型参数。
  • 机制必须分两段讲： 离线准备（文档解析 → 切片 → 向量化 → 入库）与 在线问答（查询改写 → 检索 → 重排 → 拼进提示 → 生成）。 只讲「向量检索」是不完整的，因为很多问题出在切片和重排，而不是检索本身。
  • 必须写清的现状：到 2026 年， 混合检索（关键词 + 向量）、重排器、以及「能真正衡量检索质量」的评估， 已经是默认配置而非高级选项。这一句能防止用户把 demo 当生产。
  • 必须澄清的误会： RAG 与微调不是二选一——通常的答案是「先检索」， 检索解决不了（例如需要改变输出风格或固定的推理模式）再考虑微调。 RAG 也不等于「接上知识库就准」：切片质量、召回率、重排效果决定了它的上限。
  • 上手动作（约 30 分钟）：拿 5 份真实文档跑一次检索， 然后故意问一个「资料里没有」的问题， 看系统如何处理「检索不到」这种情况。 观察点是「兜底行为」——这是判断一个 RAG 系统是否可用的最快方法。
这五条的共同结构

五个示范里反复出现的是同一个骨架： 一句定位 → 真实机制（有名字、有角色、有流程） → 必须澄清的误会 → 上手动作 → 权威来源。 其中「必须澄清的误会」这一栏是当前词库完全空白的部分， 也是用户真正卡住的地方。 建议把它固化为所有核心词条的必填字段。

十、值得肯定的部分

这份报告的措辞是严厉的，但需要明确：问题集中在内容治理这一块， 而工程与结构侧的水平明显在平均线以上。以下是审计中确认站得住的部分， 它们也是后续改造可以直接依赖的基础：

  • 板块命名有唯一事实源—— src/config/sections.ts 强制「一个板块一个名字」， 并在文件头记录了曾经的事故与现在的约定。这是正确的治理方式。
  • 顶栏已从两套名词收敛到三项，支撑层下沉页脚—— 说明团队能识别并修复信息架构问题。
  • 90 道题有契约校验—— check-learning-bank.ts 会逐题检查形态， 不达标直接让构建失败。这是整个项目里最好的工程实践， 值得原样复制到内容侧。
  • 答题页的续接逻辑做得好——上一题 / 下一题齐备， 且下一题是按「未答的第一题」智能计算的，答完能自动推进，不需要回列表。
  • 词条互链 801 条，0 死链——生成过程保证了引用有效性。
  • 词条有来源引用、核验日期与修订入口—— 每个词条都有 sources、verifiedAt， 页面上有「提交修订建议」的出口。这个机制是对的， 问题只在引用的内容与正文不匹配。
  • 有性能预算与设计守卫—— performance-baseline.json 卡体积， pnpm check:design 禁止中间字重并要求字重落差 ≥ 300。
  • 有锁定设计系统—— design.md 记录了主题、字体、间距、动效立场与页面家族， 并明确说明「display 与 body 共用同一中文字面是刻意的决定」及其性能理由。 这份文件的质量很高。
  • 「阅读路线」这个机制本身是对的—— 按目标场景而非学科串联词条，正是本报告建议的方向。 它需要的不是重做，是扩大覆盖 + 提到主路径。

一句话：这个站缺的不是能力，是把已有的能力用在了内容侧。
