一整改总则：5 条不可违背的硬约束

这 5 条不是风格建议，是防止整改本身变成新一轮事故的护栏。任何一张工单与之冲突，以本节为准。

约束 1 · 两套坐标必须同时存在

13 个领域是查阅坐标（我知道要找什么），8 站链路是学习坐标（我不知道要找什么）。 不允许用链路替换领域，也不允许把链路做成第 14 个领域。每个词条同时拥有两个位置。

约束 2 · 取消配额，不取消结构

最容易误伤的一条 domainsSchema 的 .length(13) 是内容量配额，必须删（它逼出了 325 条里的近义碎片）； chain.yml 的 8 站是结构定义，必须保留定长校验。 两者的区别是：配额规定「必须有多少条内容」，结构规定「有哪几个位置」。删前者的同时保留后者。

约束 3 · 门禁分级生效，不搞全库一刀切

当前 325 条里有 220 条逐字复用模板句。如果新门禁一上来就全库 fail，CI 会立刻红，团队会绕过它。 所以门禁必须支持按档位生效：A 档强制、B 档警告、C 档豁免。I0 建骨架（warning-only）， A 档重写完成后（I6）再转 fail。这是能让门禁活下来的唯一路径。

约束 4 · 模板结构可以留，模板句子必须清空

八段结构本身不是问题，「来源与修订」这一节甚至是好设计。问题在于八段里填的是同一批句子。 所以整改动作是换血不是换骨：保留段落骨架，重写段落内容。

约束 5 · 不重写 325 条，也不删掉它们

人力集中在 A 档 40–60 条（链路核心 + 五个点名概念）。B 档约 100 条补一句边界。 其余走 status: deprecated + replacedBy 降级——这两个字段 schema 里已经有了， 直接用，不需要新造机制。

一个顺序陷阱 termSchema 结尾是 .strict()：未在 schema 里声明的字段会让解析直接抛错。 所以凡是要给词条加新字段，必须先改 schema（I0-02），再写内容。 顺序反了，本地会报 [SCHEMA] ...#$.chain: Unrecognized key。

I0-02

扩展 termSchema：新增 5 个字段，支撑链路定位与边界声明

LN-01 KB-01 工程
改动

在 src/lib/content/schema.ts 的 termSchema（69–90 行）里追加以下字段。 全部声明为 optional——325 条存量不可能同一天填完，强制必填会让全站立刻构建失败。 「A 档必填」这件事交给门禁（第十一节）按档位执行，不写在 schema 里。

// src/lib/content/schema.ts —— 追加进 termSchema 的 .object({...}) 内
chain: z.number().int().min(1).max(8).optional(),
chainRole: z.enum(['intro', 'core', 'advanced']).optional(),

boundaries: z.object({
  solves:    z.string().min(10),
  notSolves: z.string().min(10),
  confusions: z.array(z.object({
    with:       stableIdSchema,    // 必须是真实存在的词条 id
    difference: z.string().min(10),
  })).min(1).max(3),
}).strict().optional(),

minAction: z.string().min(10).optional(),
为什么
  • chain + chainRole：让每个词条知道自己「在理解路径的第几站、本站扮演什么角色」。这是双坐标的第二根轴。
  • boundaries：把诊断里最关键的空白补上——词条回答「它不解决什么」和「它和邻居差在哪」，而不只是「它是什么」。
  • boundaries.confusions[].with 用 stableIdSchema 而不是自由文本：这样「MCP vs Function Calling」是一条可校验的引用，能被门禁检查、也能自动渲染成对比链接。
  • minAction：把「亲自试一下」从散文变成结构化字段，门禁才好判断它是不是空动作。
验收
  • 给任意一条测试词条填上全部 5 个字段，pnpm sync 与 pnpm check 均通过
  • 故意填一个不存在的 confusions[].with，确认能被校验捕获
  • 不填任何新字段的存量词条仍然照常构建
$ pnpm sync && pnpm check && pnpm validate:data
风险

.strict() 是双向的：一旦字段声明进 schema，拼错字段名也会报错。 好处是内容侧写错立刻被发现，代价是要求内容团队严格按字段名书写。请把字段名单独出一页交底。

I0-04

新建质量报告脚本：把 7 个指标打印出来（先只读，不改内容）

根因四 工程
改动

新建 scripts/report-content-quality.ts，输出人类可读摘要 + 机器可读 JSON （reports/content-quality.json，加进 .gitignore 或按需提交）。

// scripts/report-content-quality.ts —— 度量项
1. 模板复用率        正文句子在 ≥N 条词条中重复出现的比例      （当前 220/325 = 67.7%）
2. 小节结构一致度    共用同一组 h2 的词条占比                  （当前 8/8 × 325 = 100%）
3. 链路覆盖率        已打 chain 字段的词条 / 全库               （当前 0/325）
4. 题目挂接率        A 档词条中被 ≥1 道题引用的比例             （当前 0）
5. 案例反链率        被 ≥1 个案例 referenceIds 引用的比例
6. 图谱语义比        人工关系边 / 全部边                        （当前 20/333 = 6.0%）
7. 孤立词条数        在图谱中度为 0 的词条数
8. 近义碎片簇        同域内 nameZh/nameEn 存在包含关系的簇数

实现要点：句子切分按中文标点与换行做，不要引第三方 NLP 库（会撑爆依赖体积， 这个项目的性能预算卡得很紧，见 src/data/performance-budget.ts）。 「模板复用」用最朴素的方法即可——把每句话 normalize 后放进 map 统计出现次数，重复率自然浮出来。

验收
  • 脚本跑出的数字与诊断报告基本吻合（325 / 220 / 100% / 0 / 0 / 20:333）
  • 不写入任何内容文件，纯只读
  • 输出 JSON 可被后续门禁复用，避免两套切句逻辑
$ pnpm report:content
风险

切句规则直接决定「模板复用率」这个数字。规则一旦定下就冻结，并在脚本顶部注释里写清， 否则每次微调数字都会变，团队会开始怀疑指标而不是修内容。

  • 分界线（用户最常问）：路径由人预先定死的是 Workflow；路径由模型在运行时决定的是 Agent。 两者不是先进与落后，而是适用场景不同——流程稳定就该用 Workflow，因为它可预测、可审计。
  • 机制：工具调用是「能动手」的开关（模型输出结构化指令 → 外部程序执行 → 结果回喂 → 模型基于结果继续）； 记忆分短期（上下文窗口内）与长期（写入外部存储）；自主度是可调的旋钮而不是有/无的开关。
  • 风险：一旦允许写文件、跑命令、发消息，错误性质就从「说错话」升级为「做错事」。护栏、权限控制、人类可否决是必需品。
  • 上手：给模型两个工具（读文件 + 写文件），交给它一个多步任务，观察它在哪一步需要你介入。观察点是「介入点出现在哪里」，直接对应生产环境的审批设计。
验收
  • 含 Agent vs Workflow 的一句话分界线
  • 明确写出「自主度是可调旋钮」而非二元开关
  • 上手动作的观察点是「介入点」而不是「结果好不好」

门禁检查什么判定算法生效档位挡住的失败模式
1 · 模板复用 新词条与既有词条的正文相似度 句子级 normalize 后统计「同一句出现在 ≥N 条词条中」；另计两两 Jaccard 上限。切句规则一旦冻结不得调整。 A 档 fail / B 档 warn / C 档豁免 再次出现「220 条逐字同句」

门禁骨架（沿用题库校验已验证的写法）

// scripts/check-content-quality.ts
const issues: string[] = [];
const fail = (message: string) => issues.push(message);

const STRICT = process.argv.includes('--strict');
const TIERS = loadTermTiers();          // reports/term-tiers.csv

for (const term of terms) {
  const tier = TIERS.get(term.id) ?? 'C';

  // 门禁 2 · 边界声明
  if (tier === 'A') {
    if (!term.chain) fail(`${term.id} 缺少 chain`);
    if (!term.boundaries) fail(`${term.id} 缺少 boundaries`);
    // …
  }

  // 门禁 3 · 上手动作
  if (/写下三件事|再在本站搜索相邻词条/.test(body)) {
    fail(`${term.id} 的「亲自试一下」命中空动作黑名单`);
  }
}

if (issues.length > 0) {
  const header = STRICT ? '内容质量门禁未通过' : '内容质量问题（警告模式，不阻断）';
  const hint = '修复建议：见《迭代开发说明书》第十二节「决策页内容规范」';
  const error = new Error(`${header}：\n- ${issues.join('\n- ')}\n\n${hint}`);
  if (STRICT) throw error;
  console.warn(error.message);
}
设计要点 失败信息必须包含「怎么修」的提示与文档指路。一个只会说「违规」的门禁会被绕过， 一个会指路的门禁才会被使用。这条在门禁 4 转 fail 的时候尤其关键。

十二决策页内容规范

这份规范是内容团队的唯一依据。判定一条词条写得好不好，标准只有一条： 读者读完，能不能向同事复述出它的边界。

一条决策页词条的完整骨架

一句定位
  ↓
真实机制（有名字、有角色、有流程）
  ↓
必须澄清的误会（X ≠ Y，且 Y 是真实词条）
  ↓
上手动作（可完成的最小任务 + 观察点）
  ↓
权威来源（讲这个主题本身的源，不是相邻主题的博客）

其中「必须澄清的误会」是当前词库完全空白的部分，也是用户真正卡住的地方。 建议把它固化为所有核心词条的必填字段（boundaries.confusions）。

七个必须记住的踩坑点

  1. .strict() 是双向的。先声明字段再写内容；字段名拼错也会报错，这对内容团队是好事，但要提前交底。
  2. sectionLinks 与正文 h2 是手工同步的两处。没有机制保证一致，构建也不会报错。改模板必须两处一起改，并补一条门禁。
  3. 填充边的生产链在 catalog-generation.ts，不在关系数据里。只删 catalog-relations.yml 不切断生成函数，下次 generate:data 又会回来。
  4. generate:data 之后必须跑 git diff --exit-code -- src/generated。 改了数据不重新生成，CI 会以最难懂的方式失败。
  5. 性能基线不要静默调高。新增页面若超预算，先想办法复用现有资源；确需调基线时写清理由。
  6. 一个板块只允许一个名字。这个项目历史上因为两套叫法出过信息架构事故， sections.ts 的文件头注释里留着记录。新页面从那里取名字。
  7. .hallmark/ 目前被 git 跟踪（.gitignore 里没有它）。 它是设计工具的过程产物，建议加入 .gitignore 并从跟踪中移除，避免每次跑设计流程都产生无关 diff。
