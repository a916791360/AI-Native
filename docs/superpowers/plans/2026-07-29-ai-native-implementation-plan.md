# AI-Native 详细实施计划

- 状态：已于 2026-07-29 书面批准；阶段 0-8 已完成，阶段 9 基础批已完成核验
- 日期：2026-07-30
- 上游规格：`docs/superpowers/specs/2026-07-29-ai-native-design.md`
- 计划目标：把已确认的产品与技术方向拆成可独立实施、验证和验收的工作阶段
- 首版边界：静态内容站，不含账号、后端 CMS、AI 问答、资讯流、付费或社区

## 1. 实施原则

1. 先验证闭环，再扩大数量。先用 12 个代表词条跑通内容、搜索、关系、路线、页面和质量管线，再导入 300-500 个目录词条。
2. 内容和平台并行，但数据契约先行。内容作者只能在 Schema、模板、状态规则和来源格式确定后批量生产。
3. 目录数量和深度内容分别验收。`catalogued` 词条不能伪装为完整文章，`verified` 词条必须通过更严格的内容门禁。
4. 每个阶段都必须产生可运行或可检查的结果，不使用“完成大部分”作为阶段出口。
5. 搜索和图谱是增强能力，不是基本访问的前提。脚本失败时仍能浏览领域、词条和关系列表。
6. 首版保持静态架构。任何数据库、登录、向量检索、服务端渲染或运行时内容 API 都视为范围变更。
7. 未获得发布授权前，只建设持续集成，不配置可触发线上发布的工作流。
8. 正式视觉先走 `$huashu-design` 三方向 Gate。Skill 用于高保真 HTML 原型和视觉验证，选定后再转译为 Astro 生产组件。

## 2. 已确定的工程决策

### 2.1 运行时与包管理

- Node.js 24 LTS，使用 `.nvmrc` 固定主版本，并在 `package.json#engines` 声明兼容范围。
- pnpm，提交 `pnpm-lock.yaml`，在 `package.json#packageManager` 固定实际使用版本。
- TypeScript 开启严格模式，不允许业务数据通过 `any` 绕过校验。
- 使用 ESM，与 Astro 默认工程方向一致。

选择 Node.js 24 的原因是它在计划编写时处于 LTS，Node.js 20 已结束维护；不采用仍处于 Current 阶段的 Node.js 26。

### 2.2 应用框架与内容层

- Astro 作为静态站框架，使用当前稳定主版本并锁定精确依赖版本。
- 使用 Astro Content Collections 的 `glob()` loader 加载本地 MDX，并使用 Zod Schema 校验。
- 词条采用“一词一文件”，便于审查、修订、归属和 Git 历史追踪。
- 关系独立存储，词条正文不重复维护反向边。
- 路线采用独立 Content Collection，并引用稳定词条 ID。

### 2.3 搜索

搜索由两个结果源合并：

1. 构建生成的轻量词条注册表，负责中文名、英文名、缩写和别名的精确、前缀及标题模糊匹配。
2. Pagefind 静态全文索引，负责正文检索、摘要和领域、难度、状态筛选。

客户端聚合器按产品规格规定的顺序合并、去重和排序。Pagefind 官方文档确认其扩展版本支持中文无空格文本分词，也支持过滤和自定义 JavaScript API，但必须通过本项目的中文固定样本测试后才能通过技术门禁。

### 2.4 图谱

- Cytoscape.js 只在概念图谱页和需要交互的局部关系区按需加载。
- 全量图和局部图都从同一份关系数据生成。
- 移动端默认使用局部关系和结构化列表，不加载完整全量图。
- 图谱组件必须提供加载中、空数据、布局失败和脚本失败状态。

### 2.5 测试与质量工具

- `astro check`：Astro 和 TypeScript 静态检查。
- Vitest：数据转换、搜索排序和关系规则单元测试。
- Playwright：关键用户路径、响应式和降级行为测试。
- `@axe-core/playwright`：自动化无障碍基线检查。
- ESLint、`eslint-plugin-astro` 与 Prettier：代码和 Astro/MDX 格式约束。
- 自研 TypeScript 校验脚本：跨集合引用、内容状态、来源和图关系规则。

### 2.6 首版信息架构映射

六类正式页面必须全部实现，并在验收记录中使用以下名称：

1. 首页
2. 知识图鉴
3. 学习路线
4. 词条详情
5. 概念图谱
6. 内容方法

四条首发学习路线固定为：

1. AI 零基础入门
2. 高效人机协作
3. AI 产品与场景判断
4. RAG 从零到理解与应用

路线名称可以在后续书面决策中调整展示文案，但路线 ID、目标人群、学习目标和内容范围必须保持可追踪，不能在页面实现时自行删减。

## 4. 数据契约

### 4.1 稳定标识与 URL

- 词条 ID：小写 ASCII kebab-case，例如 `large-language-model`、`retrieval-augmented-generation`。
- 文件名必须与 ID 一致；领域目录不参与 ID。
- 公开 URL：`/terms/{id}/`。
- ID 发布后不可复用；名称变化不改变 ID。
- 术语被替代时使用 `deprecated` 状态和 `replacedBy`，旧 URL 永久保留。
- 路线 ID 和领域 ID 遵循同样规则。
- 中文名称、英文名称、缩写和别名均不是主键。

### 4.2 领域模型

`src/data/domains.yml` 每项至少包含：

```yaml
- id: data-retrieval-rag
  order: 6
  nameZh: 数据、检索与 RAG
  nameEn: Data, Retrieval and RAG
  shortNameZh: 检索与 RAG
  description: 一句话领域说明
  ring: core
```

规则：

- 领域 ID 唯一，`order` 在 1-12 内唯一。
- `ring` 只允许 `core` 或 `extended`。
- 领域删除前必须先迁移所有词条和路线引用。

### 4.3 词条模型

词条位于 `src/content/terms/{domain-id}/{id}.mdx`。Frontmatter 目标结构：

```yaml
id: retrieval-augmented-generation
nameZh: 检索增强生成
nameEn: Retrieval-Augmented Generation
abbreviations:
  - RAG
aliases:
  - value: 检索增强生成技术
    language: zh-CN
summary: 在生成回答前先检索外部资料，并把结果提供给模型。
domain: data-retrieval-rag
difficulty: intermediate
ring: core
status: verified
priority: 1
featured: true
publishedAt: 2026-08-01
updatedAt: 2026-08-01
verifiedAt: 2026-08-01
sources:
  - id: lewis-2020-rag
    type: paper
    title: Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks
    url: https://arxiv.org/abs/2005.11401
    publisher: arXiv
    publishedAt: 2020-05-22
    accessedAt: 2026-08-01
```

枚举：

- `difficulty`：`beginner`、`intermediate`、`advanced`。
- `ring`：`core`、`extended`。
- `status`：`catalogued`、`draft`、`verified`、`needs-review`、`deprecated`。
- `priority`：1-5，1 为首发最高优先级。
- `source.type`：`paper`、`standard`、`law`、`official-doc`、`textbook`、`course`、`research-institute`、`engineering-practice`、`media`、`personal`。

条件规则：

- 所有状态都必须具备 ID、中英文名、摘要、领域、难度、圈层和状态。
- `catalogued` 不要求正文和来源，但页面必须明确显示“已收录，待完善”。
- `draft` 不进入默认公开索引；本地预览可通过显式开关查看。
- `verified` 必须具备完整八段正文、至少两个来源、`publishedAt`、`updatedAt` 和 `verifiedAt`。
- `needs-review` 保留页面与历史内容，但显示显著复核提示，并从推荐内容中排除。
- `deprecated` 必须填写 `deprecationReason`；存在替代词条时必须填写 `replacedBy`。
- 别名匹配忽略大小写、全角半角和首尾空白后不得冲突。
- 缩写统一存储显示形式，搜索时同时生成小写归一化形式。

### 4.4 深度词条正文契约

`verified` 词条使用固定二级标题 ID：

```mdx
## 它是什么 {#what-it-is}

## 为什么需要它 {#why-it-matters}

## 它如何工作 {#how-it-works}

## 真实例子 {#example}

## 什么时候适合与不适合 {#tradeoffs}

## 亲自试一下 {#try-it}

## 接下来学什么 {#next}

## 来源与修订 {#sources-and-revisions}
```

正文约束：

- 关键事实通过来源 ID 引用，不在正文复制完整 URL。
- 首次出现的站内术语优先使用 `TermLink` 组件。
- 视觉解释必须附等价文字说明。
- “适合与不适合”必须同时包含收益、前提、限制和代价。
- “亲自试一下”必须有目标、步骤和判断标准，不能只有开放式提问。
- 快速变化的信息必须标注版本或时间边界。

### 4.5 关系模型

`src/data/relations.yml` 是关系唯一事实源：

```yaml
- id: rag-requires-retrieval
  source: retrieval
  target: retrieval-augmented-generation
  type: prerequisite
  explanation: 先理解检索如何找到相关资料，才能理解 RAG 如何为生成阶段提供上下文。
```

类型和方向：

- `prerequisite`：`source` 是应先理解的概念，`target` 是目标概念。
- `component`：`source` 是组成部分，`target` 是包含它的系统或方法。
- `comparison`：语义对称；文件中按 ID 字典序只存一条。
- `application`：`source` 是基础概念或方法，`target` 是应用、产品或业务场景词条。

关系校验：

- ID、`source + target + type` 组合唯一。
- 端点必须存在，禁止自连接。
- `prerequisite` 和 `component` 分别检查有向循环。
- `comparison` 自动生成双向展示，不生成重复数据。
- 每条边必须有 20-120 个中文字符的解释。
- 每个 `verified` 核心词条至少有一条入边或出边；显式白名单除外。
- 构建阶段生成反向关系和每个词条的一层局部图。

### 4.6 学习路线模型

路线位于 `src/content/routes/{id}.mdx`，包含：

- ID、名称、摘要、目标人群、前置知识、学习目标。
- 预计词条数量，不提供虚假的完成百分比。
- 有序章节，每章包含标题、过渡说明和有序词条 ID。
- 完成后的能力描述。
- 状态：`draft` 或 `published`。

规则：

- 发布路线不得有空章节或无效词条引用。
- 发布路线引用的核心学习节点必须为 `verified`。
- 同一路线不得重复引用同一词条，除非在数据中填写复习原因。
- 路线顺序不得违背已声明的前置关系；允许例外，但必须填写解释。

## 5. 代表性纵向切片

在批量内容导入前，使用以下 12 个词条验证完整系统：

1. `artificial-intelligence`
2. `generative-ai`
3. `large-language-model`
4. `token`
5. `context-window`
6. `hallucination`
7. `embedding`
8. `document-chunking`
9. `retrieval`
10. `vector-database`
11. `reranking`
12. `retrieval-augmented-generation`

选择理由：这组内容横跨基础认知和 RAG，包含中文名、英文名、缩写、前置、组成、比较、应用、基础与进阶难度，并可组成一条最小学习路线和足够复杂的局部图。

切片必须同时完成：

- 12 个可浏览词条，其中至少 8 个达到 `verified`。
- 一条完整的 RAG 试验路线。
- 四类关系的真实样例。
- 首页、图鉴、路线、词条、图谱、方法页和 404。
- 中文、英文、缩写和别名搜索。
- 正常、空、错误和降级状态。
- 桌面与移动端关键路径测试。

这不是“缩小后的上线版”，而是扩大生产前的工程与内容样板。

### 产品批选题 Gate（product-1）

- 第一波“场景匹配”：AI 应用场景、问题方案匹配、AI 能力边界、模型能力、任务成功率。
- 第二波“方案选择”：模型 API、模型路由、备用模型、成本优化、延迟预算。
- 第三波“人机控制”：人机协作、用户控制权、不确定性呈现、人工监督、人工升级处理。
- 第四波“质量风险”：置信度校准、离线评估、在线评估、可观测性、AI 风险管理。
- 20 个词条均为未进入深度生产的 `catalogued` 状态，与前三个批次没有重复分配，并已有公开关系入口。

- 桌面：1440x900、1280x800、1024x768。

### 任务型验收

## 8. 风险与应对

| 风险                      | 影响                     | 早期信号                           | 应对                                                         |
| ------------------------- | ------------------------ | ---------------------------------- | ------------------------------------------------------------ |
| 80-120 篇深度内容规模过大 | 上线长期推迟             | 样板批单篇研究和复核时间持续超预期 | 先测样板批吞吐；保持验收质量，不把草稿改标为已核验           |
| 300-500 词分类边界不稳定  | ID、别名和关系反复返工   | 同义概念频繁新增、领域归属争议     | 先做候选表和归并评审，再冻结首版 ID                          |
| 中文搜索相关性不足        | 核心查词任务失败         | 精确词以外的固定样本首位错误       | 双层索引、固定样本门禁、先调索引与权重，不直接升级为向量后端 |
| 全量图谱性能或可读性差    | 页面卡顿、节点噪声       | 500 节点合成测试交互延迟           | 局部图默认、筛选、按需加载、必要时预计算位置                 |

| 私有仓库 Pages 策略不符   | 发布时被权限或可见性阻断 | Pages 设置与预期不一致             | 发布阶段单独验证并保留替代静态托管方案                       |

## 9. 质量责任边界

### 自动化负责

- 字段、枚举、日期和引用格式。
- 稳定 ID、别名冲突和跨集合引用。
- 关系循环、重复、自连接和孤立节点。
- 路线空章节和无效引用。
- 已核验内容的结构、来源数量和日期。
- 搜索固定样本、页面关键路径和无障碍基线。

### 人工评审负责

- 事实是否被来源真正支持。
- 来源是否独立、可靠且适合该主张。
- 中文解释是否对初学者成立。
- 例子、边界和代价是否准确。
- 关系解释是否有学习价值，而不只是形式上连线。
- 视觉是否真正帮助理解。

自动化通过不等于内容正确；人工认为正确也不能绕过结构化门禁。

## 10. Git 与交付策略

- `main` 保持可构建；实施工作使用 `codex/` 前缀功能分支。
- 每个阶段尽量拆成独立 PR，避免把工程骨架、内容批量和视觉重构混为一个变更。
- 内容批次按领域或路线拆分，单个 PR 保持可人工核验。
- 生成文件与源数据同一 PR 提交。
- 不提交 `.env`、访问令牌、浏览器状态或本地研究缓存。
- 不在没有用户明确指令时推送、创建 PR 或部署。

建议 PR 顺序：

1. `foundation/repository-and-astro`
2. `content/schema-and-validation`
3. `design/page-system`
4. `content/vertical-slice`
5. `search/hybrid-search`
6. `graph/concept-explorer`
7. `pages/complete-information-architecture`
8. `content/catalog-batch-*`
9. `content/verified-batch-*`
10. `release/v1-candidate`
